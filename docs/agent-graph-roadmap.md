# プロンプトからエージェント艦隊へ — 14ステップのロードマップ

> 元記事（スペイン語）の日本語訳。マルチステップエージェントを「直列のチェーン」ではなく
> 「グラフ」として設計し、Claude Code の Dynamic Workflows（`agent()` / `parallel()` / `phase()` など）を使って
> エージェント艦隊を協調動作させるための実践的な考え方をまとめたもの。

マルチステップエージェントを組む人の大半は、結局まっすぐな一本道にたどり着く。
ステップ1、ステップ2、ステップ3。それぞれが律儀に前のステップの終了を待ってから動き出す。

そして、そのステップの半分は、実は何も待つ必要がなかったことにほとんど誰も気づかない。

ルーティングもしない。分岐もしない。並列化もしない。ただ列に並ぶだけ。
一つの頭脳、一つのコンテキスト、一度に一つのことだけ——コンテキストウィンドウが埋まって
エージェントが自分が何をしていたか忘れるまで。

これは、その一列縦隊をグラフに変える14ステップのロードマップだ。
艦隊全体に向けて扇状に展開し、自分自身の発見を検証し、単体のエージェントでは
到底支えきれない結果へと収束させる。

読み終える頃には、次の3つが分かるようになる。
→ 今のシステムが理由もなく待たされている箇所はどこか
→ 出力への信頼を失わずに作業をどう分散させるか
→ 品質を落とさずにコストをどう下げるか

---

## 誰も教えてくれない発想の転換

プロンプトは一文。ループは周期。ハーネスはエージェントが乗る地面。

しかし作業そのものの「形」——何が何より先に走るか、何が同時に走れるか、
何が他のすべてを待たねばならないか——その形は**グラフ**である。

ノードが考える。エッジが結果を運ぶ。

そしてClaude Codeには、それを直接組み立てるためのツールがすでに備わっている。
それが **Dynamic Workflows** だ。

Claudeは素のJavaScriptでオーケストレーション・スクリプトを書き、
それを実行する協調エージェント艦隊を起動する。
オーケストレーション自体はモデルのトークンを一切消費しない。
なぜならそれは「会話」ではなく「コード」だからだ。

ロードマップは4つのブロックで構成される。
→ 01〜04：すでに持っているグラフを見る
→ 05〜08：艦隊を動かす
→ 09〜11：出てきた結果を信頼する
→ 12〜14：破産しないようにする

---

## ブロック1・すでに持っているグラフを見る

### 01. ノードは仕事、エッジは流れるもの

グラフを構成する要素は正確に2つしかなく、これさえ明確にすればほとんどの混乱が解消する。

→ **ノード**：作業の単位。1つのエージェント、範囲の定まった仕事、1つの入力、1つの出力。
→ **エッジ**：依存関係。「このノードの出力が、あのノードの入力を満たす」という意味だけを持つ。

よくある間違いは、「〜して、それから」を無条件にエッジだと扱ってしまうことだ。

「このファイルを要約して、それから天気を教えて」には、2つの部分の間にエッジは存在しない。
天気予報は要約結果を消費しない。これは、直列スクリプトが何の必要もなく
つなぎ合わせている、2つの無関係なノードにすぎない。

エッジが存在するのは、データが本当に横断するときだけだ。

これを箱と矢印で描いてみるといい。箱は `agent()` の呼び出し。
矢印は、あるエージェント呼び出しの `return` から出てきた変数が、
別のエージェント呼び出しのプロンプトに入っていく経路だ。

矢印が描けないなら——変数が何一つ横断していないなら——その2つの箱は独立している。

そしてその独立性こそが、この後の13ステップで活用していくものだ。

→ **ルール**：エージェントの「〜して、それから」のたびに、次のステップが前のステップの
出力を読んでいるかを問え。読んでいないなら、その待ち時間は捨てられた時間だ。

### 02. 直列スクリプトはすでにグラフである。ただし退化した形で

エージェントを「Aをして、次にBをして、次にCをして、次にD」と書いた時点で、
すでにグラフを描いている。枝分かれのない鎖。各ノードは入力エッジ1本、出力エッジ1本しか持たない。

動きはする。だが遅く、脆い。鎖には冗長性がないからだ。
Cが詰まればDは永遠に起きず、Aの成果は行き場を失って上流に取り残される。

グラフエンジニアリングの最初の本当のスキルは、この鎖を描き直すことだ。

直列のエージェントを取り出し、矢印1本ごとにステップ01の問いを自分に投げかける。

ほとんどの鎖には、データを運んでいない矢印が2〜3本ある。
それらはただ、あなたがタイプした順番だからそこにあるだけだ。

そのエッジを切り落とせば、鎖はもっと幅の広い何かへと崩れ落ちる——
すべてを同時に走らせられる独立したノードがいくつかあり、
それらすべてを本当に必要とする単一のノードへと合流していく。

これは金がかからず、新しいツールも要らず、たいてい買えるどんなものよりも
多くの待ち時間を消し去る。

→ **ルール**：何かを付け加える前に、データを運んでいないエッジを消せ。

### 03. すべてのノードに契約を持たせる

推論できないノードは並列化できないノードだ。

解決策は契約だ。範囲の定まった入力、範囲の定まった出力、1つだけの仕事。

→ 入力とは、ノードが読むもの。明示的に渡され、共有ウィンドウから推測されることは決してない
→ 出力とは、定義された形。理想を言えば検証済みで、次のノードが推測なしに消費できる

ワークフローの中では、この契約は **schema** によって強制される。
Claudeに `agent()` 呼び出しとJSON schemaを渡すと、サブエージェントは
有効な構造化データを返すことを強制される。検証はツールコール層で行われるため、
形が合わなければ再試行が発生する。あなた自身が自由記述のテキストをパースして
うまくいくよう祈る必要はない。

```js
// 本物の契約を持つノード：範囲の定まった入力、検証済みの出力、単一の仕事
const ITEM = {
  type: 'object',
  additionalProperties: false,
  properties: {
    titulo:  { type: 'string' },
    url:     { type: 'string' },
    impacto: { type: 'string', enum: ['alto', 'medio', 'bajo'] },
  },
  required: ['titulo', 'url', 'impacto'],
};

const salida = await agent(fuente.prompt, {
  label: `research:${fuente.key}`,
  schema: ITEM,
  agentType: 'general-purpose',
});
```

これが、Claudeがグラフに配線できるノードと、人間が読んだときだけ機能するノードとの違いだ。

→ **ルール**：ノードの出力に形がないなら、それはノードではない。ただの会話だ。

### 04. エッジもまた契約であり、しかもタダである

エッジは「BはAの後に来る」ではない。「Aはこの形を生み出し、Bはこの形を
消費するように作られている」という、横断するものについての約束だ。

エッジを順序ではなくデータで名付けると、2つのことが簡単になる。

→ そのエッジが本物かどうかを即座に判断できる。何かがそこを移動しているかを問えるからだ
→ 形さえ保たれていれば、両端のどちらのノードでも、グラフを壊さずに差し替えられる

実際には、エッジは素のJavaScriptの中に存在する。ファンアウトと統合の間にある
「還元」ステップ——平坦化、重複排除、フィルタリング——は、ノードが返した形に対して
操作するだけのコードだ。

そこにエージェントは一切要らない。

そしてこれが、グラフ思考が静かにもたらす勝利の一つだ。人々がトークンとして
払っている膨大な量は、実は「エッジ」であり、エッジはタダなのだ。

「結果を結合する」ためにエージェントを起動したくなる誘惑があるが、それに抗え。

結合が平坦化と重複排除を意味するなら、それは `flatMap` と `Set` だ。
決定論的で、瞬時で、トークンはゼロ。

→ **ルール**：エージェントは判断のためにある。配管のためではない。
すべてのエッジがエージェントであるグラフは、自分自身の配線に家賃を払っている。

## ブロック2・艦隊を動かす

### 05. `parallel()` でファンアウトする

これが、他のすべてに元を取らせる一手だ。

独立したN個のノードがあるとき——問い合わせるべきN個のソース、
レビューすべきN個のファイル、監査すべきN個の経路——それらを鎖でつなぐのではなく、
Claudeに扇状に展開して同時に走らせるよう指示する。

ワークフローの中でそれが `parallel()` だ。サンクの配列を受け取り、
サンク1つにつきサブエージェント1体を起動し、すべてを同時並行で実行し、
結果の配列を返す。

これを頑健にしている2つの詳細がある。

→ `parallel()` はバリアだ。次のステージが結果の全体集合を見られるように、
すべてのサンクを待ってから返す
→ 例外を投げたサンクは `null` に解決される。ロット全体を巻き添えにすることはない。
不安定な1体のエージェントが実行全体を沈められない

だからこそ出力には必ず `.filter(Boolean)` をかける。

並行度はおおむねコア数で頭打ちになり、超えた分はキューに積まれる。
だから100個のサンクを渡してもすべて終わる。ただし何個かずつのまとまりで。

```js
phase('Research');

const bruto = await parallel(
  FUENTES.map((f) => () =>
    agent(f.prompt, {
      label: `research:${f.key}`,
      phase: 'Research',
      schema: ITEM,
      agentType: 'general-purpose',
    }),
  ),
);

const recogido = bruto.filter(Boolean);   // 落ちたエージェントのnullを除外
```

そして重要なのはここだ。ファンアウトはClaudeが書いたコードの中に存在するのであって、
モデルとの会話の中には存在しない。

Claude自身のコンテキストが9つのソースを同時に抱え込むことは決してない。
各サブエージェントが自分のソースを読み込み、最終的な回答だけを返す。

これによって、セッションを窒息させることなく、数十から数百のサブエージェントへと
スケールできる。オーケストレーション層のコストがゼロなのは、それがClaudeが
考えるもう一つのターンではないからだ。

→ **ルール**：N個のものが互いを読み合わないなら、キューに並べるな。展開せよ。

### 06. 扇をバリアで閉じる

ファンアウトは、それを回収する何かがあって初めて役に立つ。

ファンインとは、エッジが収束するノードのことだ。1つのエージェント、
あるいは一片のコードが、上流のすべての結果を一度に見て、
集合全体を必要とする何かを行う場所——ソース間の重複排除、
インパクト順の並べ替え、何一つ戻ってこなかった場合の早期終了。

それこそが、バリアが実時間のコストに見合う唯一の場所だ。

すべてのソース間で重複排除する？　バリアで正解。
単にリストを平坦化するだけ？　それはエッジだ。インラインでやれ。

```js
// エッジ：素のJS、エージェントなし、トークンゼロ
const plano = recogido.flatMap((c) => c.items);
log(`Recogidos ${plano.length} elementos`);

phase('Curar');

// バリアノード：重複排除と並べ替えのために集合全体が本当に必要
const curado = await agent(
  `Deduplica y ordena estos por impacto:\n${JSON.stringify(plano)}`,
  { phase: 'Curar', schema: CURADO },
);
```

テストはシンプルだ。「並列 → 変換 → 並列」と書いていて、
その間の変換に要素間の依存が一切ないなら、パイプラインを使ってバリアを
丸ごとスキップすべきだった、ということだ。

→ **ルール**：あるステージが本当にそれ以前のすべての結果をまとめて必要とする時だけバリアを置け。

### 07. ダイヤモンド：分割し、働き、統合する

ファンアウトとファンインを組み合わせると、まともなエージェントグラフの
作業トポロジーが得られる。それが**ダイヤモンド**だ。

1つのノードが仕事を分割する。多数のノードが並列に作業する。1つのノードが統合する。

その正準形には、覚える価値のある名前がある。**ファンアウト → リデュース → 統合**。

→ ファンアウトで幅を得る
→ 素のコードによるリデュースでそれを圧縮する
→ 回答を書く最終エージェントによる統合

これは、市場スキャン、依存関係監査、コードレビュー、リサーチレポートの背後にある骨格だ。
ソースとプロンプトを変えれば、同じ骨格が適応する。

このダイヤモンドが見えるようになると、「どうやってエージェントにもっと多くの
ステップを踏ませるか」を問うのをやめ、「分割点はどこで、統合点はどこか」を
問うようになる。それこそが本当にスケールする問いだ。

→ **ルール**：ステップを設計するな。分割点と統合点を設計せよ。

### 08. 実行時にエッジをルーティングする

すべてのグラフが固定というわけではない。時には、どのエッジを取るかが
あるノードが見つけたものに依存する。

ルーターノードは結果を検査し、どの経路が発火するかを決める。
チケットを分類して正しいハンドラーに分岐する。diffのサイズを見て、
簡易レビューか、フル監査の立ち上げかを選ぶ。

ワークフローの中では、これはノードの検証済み出力に対する単純なJavaScriptの
`if` や `switch` にすぎない。制御フローはコードの中に存在するからだ。

```js
// ルーターノード：エージェントが分類し、コードがエッジを選ぶ
const { severidad } = await agent(
  `Clasifica el riesgo de este diff:\n${diff}`,
  { schema: {
      type: 'object',
      properties: { severidad: { enum: ['baja', 'alta'] } },
      required: ['severidad'],
  }},
);

let revision;
if (severidad === 'alta') {
  revision = await parallel(ARCHIVOS.map((a) => () => agent(`Audita ${a}`)));
} else {
  revision = await agent(`Revisión rápida de ${diff}`);
}
```

ここでは決定論性は制約ではなく機能だ。

ルーターの判断はClaudeから来てよいが、ルーティング自体はコードだ。
同じ分類に対しては常に同じように走る。

ノードにはモデルの判断力、エッジにはスクリプトの信頼性。
「エージェントが監査をスキップすることに決めた」といった、創発的な驚きは起きない。
そのスキップはグラフに書かれていなければならず、実際には書かれていないからだ。

→ **ルール**：モデルには「これが何か」を決めさせ、コードには「それをどうするか」を決めさせよ。

## 反ルール（続きを読む前に）

グラフが買うのは幅であって、より良い判断力ではない。

もし作業の各ステップが前のステップの完全な全体像を必要とするなら、
それをエージェント間に分散させても、より良い答えは得られない。
同じ答えが、より高く、より遅く手に入るだけだ。

グラフが元を取り始める正確な瞬間は、作業が
「互いの結果を決して読まない仕事」に分割されるときだ。

エージェントを1体でも追加する前に、あなたの請求額を決める唯一の問いはこれだ。
——「私の作業はどこで分割されるのか？」

分割されないなら、エージェント1体のままにして、残りの6ステップは節約しろ。

## ブロック3・出てきた結果を信頼する

### 09. エッジに検証者を置く

グラフの本当のレバレッジは、エージェントを増やすことではない。
その周りに組み立てられる、信頼を生み出すための構造だ。

**検証者ノード**は、結果が下流に流れる許可を得る前に、エッジ上に座る。
その唯一の仕事は、その発見を殺そうと試みることだ。生き残れば通過する。
生き残らなければ、その発見は回答に到達することは決してない。

そしてこのすべての下には、1つの厳格なルールがある。
——同じエージェントに自分自身の答案を採点させるな。
自分の出力をレビューするモデルは、自分自身の誤りのほとんどを見逃す。
なぜなら、それは間違えたのと同じ場所から評価しているからだ。

手元に持っておくべき3つのパターン。

→ **敵対的検証**：発見1件ごとに、それを論破せよという指令を持つN人の
独立した懐疑派を起動する。多数決を生き延びた場合だけ残る。

→ **多様なレンズによる検証**：各検証者に別々の角度を与える。
「正しいか」「安全か」「再現するか」。この多様性が、N個の同一チェックでは
決して見つからない失敗モードを捕らえる。

→ **審査員パネル**：別々の角度からN個の試みを生成し、並列の審査員で採点し、
勝者から統合しつつ、僅差だった候補の良い部分を接ぎ木する。

これは、ランタイム全体を移植するといった、これまでで最も野心的な
エージェントプロジェクトの背後にあるパターンだ。敵対的レビューが最後にではなく、
ループそのものの中に組み込まれている。

→ **ルール**：検証されずに移動する発見は一つもない。そして2人の検証者が
同じ問いを投げることは決してない。

### 10. ノードを隔離し、1つの失敗がグラフ全体を汚染しないようにする

鎖の中では、失敗はカスケードする。Cが死ねばDは決して走らず、すべてが止まる。

グラフの中では、失敗はそのノードの中に封じ込められるべきだ。

これはすでに部分的に真実だ。`parallel()` の中で破裂したサンクは
`null` に解決されるので、8体の良いエージェントは戻ってくる一方で、
悪い1体だけが自滅する。`.filter(Boolean)` があなたの封じ込めだ。

すべてのファンインを、完全な集合を前提にするのではなく、
不在の入力を許容するように設計せよ。

より微妙な失敗は、ノード同士が互いに踏み合うことだ。
複数のエージェントが並列にファイルを書くと、衝突する。

解決策は隔離だ。各エージェントは自分専用のgit worktreeで走り、
サンドボックス内で自分の仕事をこなし、その後クリーンにマージされる。

これに頼るのは、ノードが本当に並列で書き込みを行う場合だけにせよ。
それを必要とする唯一のトポロジーのシートベルトであって、
すべての実行にデフォルトで課される税ではない。

→ **ルール**：1つのファイルに書き込むのは1人だけ。そしてすべてのファンインは欠落を許容する。

### 11. ループを追加してもよい。ただし収束すること

時には、実際に中に入るまで作業の大きさが分からないことがある。
未知の規模の発見。1つのバグを見つけると他に3つ見つかるバグの一斉捜索。

それが求めるのはループだ。前のノードへ戻る制御されたエッジ。

危険は明白だ。収束しないループは、予算を溶かし尽くすまでエージェントを
起動し続ける無限ループになる。

収束するパターンは **loop until dry（枯れるまでループ）** だ。
連続K回のラウンドで何も新しいものが出てこなくなるまで探索者を起動し続け、
そこで止める。

そして、うまくいくかどうかを分ける詳細——ほぼ全員が最初にやってしまう間違い——は、
「何に対して重複排除するか」だ。

**「確認済み」ではなく、「これまで見たすべて」に対して重複排除せよ。**

そうしないと、却下された発見が毎ラウンド再登場し、ループは決して枯れず、
同じ行き止まりを永遠に再発見するために金を払い続けるマシンを作ってしまう。

```js
const visto = new Set();
const confirmados = [];
let secas = 0;

while (secas < 2) {                          // 空のラウンドが2回続いたら停止
  const encontrados = (await parallel(
    BUSCADORES.map((b) => () => agent(b.prompt, { schema: BUGS }))
  )).filter(Boolean).flatMap((r) => r.bugs);

  const nuevos = encontrados.filter((b) => !visto.has(clave(b)));
  if (!nuevos.length) { secas++; continue; }  // 新規なし → 枯れに向かう

  secas = 0;
  nuevos.forEach((b) => visto.add(clave(b))); // 確認済みではなく「見た」に対して重複排除

  const juzgados = await parallel(nuevos.map((b) => () =>
    parallel(['correcto', 'seguridad', 'repro'].map((lente) => () =>
      agent(`Juzga "${b.desc}" desde ${lente}. ¿Es real?`, { schema: VEREDICTO })))
      .then((v) => ({ b, real: v.filter(Boolean).filter((x) => x.real).length >= 2 }))
  ));

  confirmados.push(...juzgados.filter((v) => v.real).map((v) => v.b));
}
```

→ **ルール**：すべてのループはラウンド数の上限を持ち、これまで見たすべてに対して重複排除する。

## ブロック4・破産しないようにする

### 12. ノード間でモデルを階層化する

すべてのノードが最高のモデルを必要とするわけではない。

グラフは、単体のエージェントでは決して得られない形でこれを明白にする。
範囲が定まった反復的なノードがある——このフィールドを抽出する、
このチケットを分類する。そして本当の判断力が宿るノードがある——
レポートを統合する、発見を裁定する。

退屈な仕事は安いモデルで走らせ、判断力が重要な場所に高価なトークンを使え。

ワークフローの中では、各サブエージェントはスクリプトが上書きしない限り、
あなたのセッションのモデルを継承する。デフォルトでは、大規模な実行の
請求はすべてあなたのセッションレベルで計上される。

個別の `agent()` 呼び出しにおける `model` オプションは、そのノードだけを
別の場所にルーティングする。

大規模な実行の前に `/model` を確認し、統合ノードは高いレベルを保ちながら、
ファンアウト内の反復的なノードのレベルを下げよ。

これが、グラフの形に手を触れずに、トークンに飢えたグラフを
経済的なものへと変えるレバーだ。

→ **ルール**：高価なモデルは判断が懸かっている場所にだけ使え。

### 13. トポロジーはあなたのコストであり、レイテンシである

グラフの形は装飾ではない。存在する中で実時間に対する最大のレバーだ。

誰もがつまずく決断——`parallel()` 対 `pipeline()`。

→ `parallel()` バリアは、次のステージが始まる前に、すべてが最も遅いノードを待つようにする
→ `pipeline()` は、各要素をバリアなしにすべてのステージへ独立に流す。
要素Aがステージ3にいる間、Bはまだステージ1にいてもよい

速い要素は、遅い要素の後ろで立ち往生する代わりに、早く終わる。

デフォルトはパイプライン。バリアに頼るのは、あるステージが本当に
それ以前のすべての結果を一度に必要とする場合だけにせよ——集合全体に対する
重複排除、合計に基づく早期終了、「他の発見」と比較するプロンプト。

「その方がきれいに見える」「ステージが分かれている感じがする」は理由にならない。
バリアのレイテンシは実時間であり、測定可能で、無駄にされている。

分かれていることと、同期していることは同じではない。

→ **ルール**：デフォルトはパイプライン。バリアは正当化された例外としてのみ。

### 14. Claudeにグラフを描かせる

最後の一手は、事前に計画できない仕事のために、グラフを手で描くのをやめることだ。

**Dynamic Workflows** では、目標を記述するだけで、Claude自身が
オーケストレーション・スクリプトを書く。タスクを分解し、ファンアウトを選び、
協調エージェント艦隊を起動し、結果を統合する。

期待して当てはめようとする固定グラフの代わりに、その特定の実行に合わせて
仕立てられたグラフが手に入る。

3つの入り口がある。

→ プロンプトの中で「workflow」という言葉を言えば、Claudeがそのタスク用に1つ書く
→ 保存済みのもの、あるいは標準で付属するものを実行する。`/deep-research` は
本番で走っている本物のグラフだ。絞り込み → 並列検索 → 取得 → 敵対的検証 → 統合。
まさにこのロードマップの骨格そのもの
→ セッション内の実質的なすべてのタスクに対してワークフローを計画するモードを有効にする

実行がうまくいったら、そのスクリプトを `.claude/workflows/` に保存せよ。
バージョン管理され、名前で再実行可能で、リポジトリをクローンした誰もが起動できる。

```
› Lanza un workflow que audite todas las rutas de src/routes/ buscando
  auth ausente. Un agente por archivo de ruta, y verifica cada hallazgo
  antes de reportarlo.

● Claude escribió un script de orquestación · lanzando en background…

  /workflows — auth-audit · running
  ✓ Acotar      1/1     2.1k tok · 4s
  ✓ Fan-out     18/18   un agente por archivo de ruta
  ◯ Verificar   11/18   escépticos a 3 votos por hallazgo…
  ○ Sintetizar  0/1     esperando a verificar

  セッションは応答可能なまま。艦隊が走っている間も作業を続けられる
```

→ **ルール**：仕事が実行のたびに形を変えるなら、グラフを描くな。記述せよ。

## 今週作るべき6つのグラフ

**すべてのルートに対するセキュリティスキャン。**
ルートファイル1つにつきサブエージェント1体。それぞれが認証チェックの欠落を狩り、
その後、レポートに到達する前にすべての発見を確認する検証パスを走らせる。
単体のコンテキストでは到底支えきれない幅。

**`/deep-research` によるソース付きレポート。**
Claude Codeにすでに組み込まれているグラフ。質問を別々の角度に分解し、
並列で検索を走らせ、ソースを重複排除し、書き上げる前に3票の懐疑派で
各主張を敵対的に検証する。

**モジュールをファイル単位で移植する。**
ファイルに対する翻訳のファンアウト、各ファイルでのゲートとしてのテストスイート、
失敗はループに戻る。敵対的レビューが、1回きりのパスなら壊れたまま
渡していたであろうものを捕らえる。

**diffの敵対的レビュー。**
サイズに応じてルーティング。小さな変更は簡易パスを受け、大きな変更は
別々のレンズ（正しさ・安全性・速さ）を持つレビュアーによる完全な並列監査を
起動し、その後審査員パネルが統合する。

**スケジュールされたエコシステムスキャン。**
一度保存すれば永遠に再実行できる。多数のソース——リリース、ブログ、フォーラム——を
並列に問い合わせ、バリアでインパクト順に並べ替え、サマリーを書く。
`.claude/workflows/` にバージョン管理され、名前で起動可能。

**未知の規模の発見。**
バグが何個あるか分からない。並列の探索者、新しい発見それぞれを
これまで見たすべてに対して重複排除、生き残ったものの検証、
2ラウンド続けて何も出なくなるまでループを続ける。そこで停止。

## 最初のグラフを起動する前のチェックリスト

→ データを運んでいないエッジは消したか？
→ 作業は本当に分割されるか、それとも各ステップが前のステップを必要とするか？
→ すべてのノードは、範囲の定まった入力・形のある出力・単一の仕事を持っているか？
→ `flatMap` で済むことのためにエージェントに金を払っていないか？
→ 集合全体を必要としないバリアはないか？
→ 誰も殺そうとしなかった発見が、結果に到達していないか？
→ 2人の検証者が同じ問いを投げていないか？
→ すべてのループにラウンド数の上限があるか？
→ 同じファイルに書き込むノードが2つ以上ないか？
→ 反復的なノードは高価なモデルで走っていないか？

3つ以上失敗しているなら、それはグラフではない。ステップが多いだけの鎖だ。

## 結論

プロンプトを書く者は質問をする。アーキテクトはグラフを描く。

直列のエージェントは決して天井ではなかった。それは単に最初の形にすぎなかった。
誰もが手を伸ばす形。なぜならそれは私たちが文章を書く方法と一致しているからだ。
一本の線、一つの頭脳、一度に一つのこと。

ノードとエッジが見え始めると、エージェントにもっと多くのステップを踏ませることを
求めるのをやめ、グラフにもっと幅を持たせることを求めるようになる。

作業が独立している場所ではファンアウトを。信頼が重要な場所ではエッジにゲートを。
判断力が懸かっていない場所では安いモデルを。

大半の人は、ステップを一列縦隊に並べ続けるだろう。

グラフを描く方法を学んだ者は、艦隊全体を動かすことになる。
そして彼らは、他の全員が詰まっている天井に、二度と気づくことはないだろう。

今夜、今のシステムを描いてみてほしい。仕事とその間の矢印だけを。
偽のエッジを数え、消し去れ。

これはこの仕事全体における最初の一手であり、コストはゼロで、
たいてい買えるどんなツールよりも多くの待ち時間を消し去る。
